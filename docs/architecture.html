1. System overview

TimeClock records when employees start and stop work, and lets an administrator review those times, correct them, and calculate pay. It has four parts:

  • ESP32 time clock mounted at a store. Employees tap an NFC card. The clock records the punch on its own flash storage first, then uploads it.
  • TimeClock API, an ASP.NET Core service hosted on Render. It is the only component that talks to the database.
  • PostgreSQL database hosted on Render. It holds employees, locations, punches, wages, pay-period state, and the clock failure log.
  • Admin web app (Next.js), run on the admin's computer. The admin manages employees, cards, wages, and punches, and reviews clock issues.
Figure 1. Components and connections. Only the API connects to the database. The ESP32 and the admin app both call the API over HTTPS with the shared admin API key.

The design rule that shapes most decisions: a scan at the clock must never wait for the network. The clock writes each punch to flash storage, shows the result immediately, and uploads in the background. The API accepts each punch exactly once, even when the clock has to retry.

3. PostgreSQL database

3.1 Databases

One Render Postgres instance hosts two databases with identical schemas:

  • timeclock_x2fo: production. The ESP32 always writes here.
  • timeclock_test: test. The admin app uses it when its environment switch (Settings page) is set to Test.

3.2 Schema management

There is no separate migration tool. The API runs database/001_CreateSchema_PostgreSQL.sql against both databases every time it starts. Every statement is idempotent (CREATE TABLE IF NOT EXISTS, ADD COLUMN IF NOT EXISTS, CREATE INDEX IF NOT EXISTS), so a deploy that adds a column or table updates the database automatically. New schema changes must follow the same rule: additive and safe to run repeatedly.

3.3 Tables

EmployeesName, email, EmployeeNumber, optional 4-digit Pin, optional NFC CardUid, home LocationId, active flag. Soft delete (IsDeleted). Employee number, PIN, and card are each unique among non-deleted employees (partial unique indexes).

4. TimeClock API (.NET 9)

4.1 Structure

  • Controllers (Controllers/) define the HTTP routes and validate input.
  • Repositories (Repositories/) hold all SQL, written by hand and executed with Dapper. Each request opens its own connection from DbConnectionFactory.
  • Models (Models/) are plain classes. Enums such as PunchType are sent as strings ("In", "Out").
  • Pay logic (Pay/PayPeriodCalculator.cs) computes 14-day periods from the anchor date.

4.2 Request pipeline

Every request passes through these steps in order (Program.cs):

  1. CORS: allows the origins in CORS_ORIGINS (default http://localhost:3000). In practice the browser never calls the API directly, because the admin app proxies all calls.
  2. Admin API key check (AdminApiKeyMiddleware): rejects any request without the correct X-Admin-Api-Key header with 401. Exempt: /api/health and CORS preflight (OPTIONS).
  3. Test database routing (TestDatabaseMiddleware): a request to /api/test/... is rewritten to /api/... and flagged, and DbConnectionFactory then connects to timeclock_test instead of production. This runs before routing, so every endpoint automatically has a test twin.
  4. Routing and controllers.

4.3 Startup

  1. Reads DATABASE_URL (a postgresql:// URL is converted to an Npgsql connection string, and SSL is required for any non-local host).
  2. On Render, binds to 0.0.0.0:$PORT.
  3. Applies the schema script to the production database, then to the test database. A failure on production stops startup. A failure on test is logged only.
  4. In Development on Windows only, shows a dialog to pick the production or test database before starting. This never runs on Render.

4.4 Main capabilities

AreaWhat the API does
EmployeesCreate, edit, soft delete. Generates the next free 4-digit employee number from 1000 upward (serialized with a Postgres advisory lock so two admins cannot get the same number). Checks number uniqueness against other employees' numbers and PINs.

5.2 How it reaches the API

The browser never calls the API directly. Every call goes to the app's own route /api/backend/..., implemented in src/app/api/backend/[...path]/route.ts. That code runs on the Next.js server (Node.js on the admin's computer). It:

  1. Builds the upstream URL from API_URL in .env.local.
  2. Adds the X-Admin-Api-Key header from ADMIN_API_KEY in .env.local.
  3. Forwards the method, body, and content type, and returns the API's response unchanged (with special handling for empty 204 responses).

Because the key lives only in server-side environment variables (not prefixed with NEXT_PUBLIC_), it is never sent to the browser.

5.3 Production and Test switch

The Settings page stores the choice in the browser's localStorage (timeclock-environment). When it is Test, lib/api.ts rewrites every /api/... path to /api/test/..., the API sends those requests to timeclock_test, and the app shows an amber "Test environment" banner. The ESP32 has no such switch: it always uses production.

6.2 Files on flash (LittleFS)

FileContentsLifecycle
/punches.jsonlUpload queue. One punch per line, already in the exact format the API expects.Appended on each punch. A line is removed only after the API accepts it (or rejects it as invalid).

/state.jsonEach employee's status today: IN, BREAK, or OUT.Updated on each punch. Entries from earlier days are ignored and pruned.

A queued punch line looks like this:

{"id":"3f2a9c1e-8b7d-4e21-9a55-0c4d2b1e7f60","employeeId":"03c85ba3-649c-4268-bdf4-5294a54476a6",
 "punchType":"In","punchedAt":"2026-11-14T08:30:00","locationId":"e1e5bd66-0268-4ab6-875e-6dfe20a12464",
 "source":"ESP32","deviceId":"esp32-A0:B7:65:12:34:56"}
  • id is a random version-4 GUID made on the clock with the hardware random number generator. It is the key to duplicate-free retries (section 9).
  • locationId is DEVICE_LOCATION_ID from secrets.h if set, otherwise the employee's home location.
  • deviceId is esp32- plus the board's Wi-Fi MAC address.

6.4 Background work

Network work runs only while the clock is idle (not showing a message and not waiting for the Break or Day choice), so it never slows a scan.

TaskWhen
Upload punches, then failuresEvery 30 seconds, and 3 seconds after a new punch or failure. Up to 20 lines per request.
Download employee listAt startup, every 15 minutes, and about 1 minute after an unknown card (at most once a minute).
Set clock timeSNTP from pool.ntp.org and time.nist.gov, time zone CST6CDT (US Central with daylight saving). Keeps retrying in the background.
Wi-FiWiFiManager. On first boot, or if the saved network fails, the clock opens a setup hotspot TimeClock-Setup for 3 minutes. Auto-reconnect is on.

6.5 Configuration (secrets.h)

Copy secrets.example.h to secrets.h (ignored by git) and set ADMIN_API_KEY to the same value as on Render. Optional: API_BASE_URL (defaults to the Render URL) and DEVICE_LOCATION_ID. If the key is empty, the clock still records punches locally but uploads nothing.

7.3 Build and deploy

  1. A push to main on GitHub triggers a Render deploy.
  2. The Dockerfile builds in two stages: the .NET 9 SDK image runs dotnet publish, then the result and the database/ folder are copied into the smaller ASP.NET runtime image.
  3. Render starts the new container. On startup the API applies the schema to both databases.
  4. Render routes traffic to the new container once /api/health answers.
Every push to main changes production. Schema changes apply to the production database on startup. Test with the admin app in Test mode, or with a local API, before pushing.
Cold starts. If the web service is on a plan that sleeps when idle, the first request after a quiet period can take 30 to 60 seconds. The clock's upload timeout is 10 seconds, so that first upload may fail. Nothing is lost: the punch stays queued and the next attempt, 30 seconds later, reaches a running service.

8. End-to-end data flows

8.1 Employee clocks in at the store

Figure 4. Clock-in sequence. The employee sees the result before any network traffic happens.

8.2 Assigning a new badge

  1. The employee taps a new card. The clock shows UNKNOWN CARD and the card ID, and queues a report.
  2. The report reaches the API. If the card already belongs to someone (assigned after the clock's last list download), the issue names that employee. Otherwise it says the card is not assigned.
  3. The admin opens Clock Issues, clicks the card button, and picks the employee. The card is saved and all open unknown-card issues for it are resolved.
  4. About a minute after the unknown card, the clock downloads the employee list again. The next tap works.

The admin can also type the card ID on the employee's page under NFC Card.

8.3 Clocking in without a badge

An employee who forgot the badge can use a 4-digit clock code. The admin generates it on the employee's page (next free number from 1000, used as both employee number and PIN). POST /api/auth/verify-pin accepts the PIN or the employee number. The ESP32 build documented here has no keypad, so this path is for a PIN-capable clock app or for the admin adding the punch by hand.

8.4 Admin corrections

The admin adds, edits, or deletes punches on the Time Clock grid. These go through the same API with Source = "Web". The clock does not learn about these edits (see section 13).

9. Offline operation and recovery

The clock is designed so that a Wi-Fi outage, an API outage, or a slow server start never loses a punch and never creates a duplicate.

9.1 Three guarantees

  1. Write first. A punch is appended to /punches.jsonl on flash before the screen confirms it. If the write fails, the clock shows SAVE FAILED instead of a false confirmation.
  2. Delete only after the API answers. Lines leave the queue only when the API replies 200 (stored) or 400 (permanently invalid, and logged to Clock Issues by the API). Any other outcome, such as no Wi-Fi, a timeout, 401, or 5xx, leaves the queue untouched for the next attempt.
  3. Retries are harmless. Each punch carries a GUID made on the clock. The API inserts with ON CONFLICT ("Id") DO NOTHING and counts only new rows. If the clock's upload reached the database but the reply was lost, the clock sends it again and the database ignores the copy.

9.2 What still works offline

  • Card lookup, names on screen, and the In or Break/Day decision all use files on the clock.
  • The clock keeps time with its internal clock once NTP has set it. It needs the network only once after power-up to learn the time.
  • New cards assigned in the admin app are not known until the clock can download the list again.

9.3 When the network comes back

Wi-Fi reconnects automatically. Within 30 seconds the clock uploads the oldest 20 queued punches; each successful batch is removed and the next batch follows on the next cycle, until the queue is empty. Punch times are the times recorded at the scan, not the upload time, so the timesheet is correct regardless of how late the upload is. Unknown-card reports follow the same pattern.

10. Security model

10.1 Trust boundaries

ConnectionProtection
ESP32 to APIHTTPS (TLS). Admin API key in the X-Admin-Api-Key header.
Browser to admin appLocal only (http://localhost:3000), on the admin's own computer. Placeholder login (see 10.4).
Admin app server to APIHTTPS. Admin API key added by the server-side proxy. The key is never sent to the browser.
API to PostgresRender's private network using the internal URL. SSL is required whenever the host is not local. Database credentials exist only in Render's DATABASE_URL, and locally in .NET user secrets.

10.2 Admin API key

  • One shared secret, configured as ADMIN_API_KEY in three places: the Render web service, the admin app's .env.local, and the clock's secrets.h. All three are excluded from git.
  • Required on every route except /api/health. Compared in constant time, so response timing does not reveal how much of a guess was right.
  • Outside Development, a missing key on the server fails closed: every request is rejected.
  • The test database routes (/api/test/...) need the same key.
  • Rotation: set a new value on Render, update .env.local and restart the admin app, and reflash each clock. Clocks with the old key keep their punches queued (401 is retried) and upload them after reflashing.

10.4 Known security gaps

Admin login is a placeholder. The login page checks a hard-coded admin / admin123, and "Sign in with Google" signs in without contacting Google. The session is only a sessionStorage flag. This is acceptable only because the app runs on the admin's own computer and the real protection is the API key on its server. Do not expose the admin app on a network or host it publicly until real authentication is added.
The ESP32 does not verify the server certificate. It uses setInsecure(): traffic is encrypted, but a device on the store network that impersonates the API could capture the API key. Fix by embedding Render's root certificate in the firmware.
One key does everything. A key pulled from a clock's flash grants full admin API access, including reading wages and deleting employees. A separate, limited clock key (sync and failure upload only) would contain that risk.
PINs are stored in plain text as 4 digits, and the admin employee list shows them. A 4-digit code is guessable by design; verify-pin has no attempt limit.
NFC card IDs can be copied. The clock trusts the card's UID, which inexpensive tools can clone. The name shown on each scan helps employees notice misuse; admins can review the DeviceId and times on punches.
Other notes. The setup hotspot password (12345678) is in the source code and only matters while the hotspot is open. Serial logs print card IDs and punch data, so the USB port should not be accessible in the store.

11. Time and date handling

  • Punch times are local wall-clock times with no time zone, for example 2026-11-14T08:30:00, stored in a TIMESTAMP (without time zone) column. The API marks incoming values as "unspecified" so .NET never shifts them.
  • The ESP32 converts NTP time to US Central (CST6CDT,M3.2.0/2, which handles daylight saving) before formatting. A clock installed in another time zone needs that string changed.
  • Shifts never cross midnight. Each punch belongs to one calendar day, and the clock resets each employee's state at midnight. A late shift that ends after midnight must be split or corrected by the admin.
  • Audit columns (CreatedAt, ReceivedAt, ResolvedAt) are true timestamps in UTC (TIMESTAMPTZ).
  • Pay periods are 14 days, counted from the anchor date on the Settings page.

13. Known limitations and recommended next steps

13.1 Behavior limits

  • In/Out state is per clock. Each clock decides In or Out from its own state.json. An employee who clocks in on one clock and out on another is recorded as In twice. Admin punch edits also do not reach the clock. A fix is to include each employee's last punch of the day in the sync download.
  • Up to 15 minutes to learn about changes other than new cards (deactivations, name changes, removed cards). Unknown cards trigger a refresh within about a minute.
  • No punch without NTP time after a power cut with no Wi-Fi. A battery-backed real-time clock module would remove this limit.
  • Queue rewrite window. After an upload the clock rewrites the queue file by writing a temp file, deleting the original, and renaming. Power loss in the instant between delete and rename would leave the remaining punches in /queue.tmp. Recovering that file at boot would close the gap.
  • No keypad on the ESP32, so badge-free clocking with a PIN requires another clock app or an admin-entered punch.
  • Unverified build. The firmware was written against the libraries listed in the README but was not compiled on the documenting machine. Compile and bench-test before installing.

13.2 Recommended next steps, by priority

  1. Real admin authentication (for example, Google sign-in verified on the server), before the admin app is reachable by anyone else.
  2. Certificate verification on the ESP32 (embed the root CA instead of setInsecure()).
  3. A separate, limited API key per clock, so a stolen clock cannot read wages or change data.
  4. Server-provided punch state in the sync download, for correct In/Out across multiple clocks.
  5. Hash PINs, hide them in the admin list, and rate-limit verify-pin.
  6. Battery-backed RTC on the clock, and recovery of /queue.tmp at boot.
  7. Automated tests for sync idempotency and the clock failure log, run before each deploy.
